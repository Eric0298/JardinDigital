# SQLite Node Vertical Slice

## 1. Objective

This vertical slice proves the first real local persistence flow in
JardinDigital: create one Node, save it to SQLite, close and reopen the Tauri
application, load the same Node with the same ID, edit it, save the edit, and
reload it. Edge, Canvas, Placement, Resource, filesystem resources, and the
production Canvas remain outside this scope.

## 2. Alternatives evaluated

| Alternative | Advantages | Costs | Decision |
|---|---|---|---|
| Official Tauri 2 SQL plugin with SQLite | Maintained in the official plugins workspace; Tauri 2 desktop support; official TypeScript binding; SQLx-backed SQLite; built-in versioned, transactional migrations; OS-specific application storage | SQL remains explicit; permissions are command-granular rather than statement-granular; adds one npm package and one Rust crate | Selected |
| Custom Rust implementation with a SQLite library | Could expose only narrow native commands and completely hide database commands from the WebView | More Rust command, serialization, connection, migration, and lifecycle code; an additional local persistence design to maintain | Rejected for this first slice |
| Store/key-value persistence | Official, small key/value API and simple for settings | Poor fit for structured entities, constraints, upserts, future relationships, and schema evolution; would turn Nodes into opaque values | Rejected for knowledge data |

The selected option has the lowest maintenance cost that still matches the
approved structured-data model. No alternative was installed for comparison.
It is portable across Tauri's supported desktop platforms and keeps a standard
SQLite file suitable for a future SQLite-aware backup design. A custom Rust
adapter would be similarly portable and more strictly testable below the
WebView boundary, but would require JardinDigital to own more connection,
command, and migration code. The key/value Store is portable and conceptually
light for preferences, but weak for relational evolution, constraints,
queryability, and consistent future backups of structured knowledge. On
maintenance, code volume, migration support, model fit, and overarchitecture
risk, the official SQL plugin is the best balance for this slice; its coarser
permission granularity is the explicit security tradeoff.

## 3. Selected solution and official sources

The implementation uses `@tauri-apps/plugin-sql` 2.5.0 and
`tauri-plugin-sql` 2.5.0 with only the Rust `sqlite` feature. The application
currently resolves Tauri 2.12.0, and the installed Rust toolchain is 1.98.1,
which satisfies the plugin's current requirements.

Official and primary sources consulted on 2026-09-29:

- [Tauri 2 SQL plugin documentation](https://v2.tauri.app/plugin/sql/)
- [Official Tauri plugins workspace](https://github.com/tauri-apps/plugins-workspace)
- [Official SQL plugin source](https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/sql)
- [tauri-plugin-sql on crates.io](https://crates.io/crates/tauri-plugin-sql)
- [tauri-plugin-sql API documentation](https://docs.rs/tauri-plugin-sql/latest/tauri_plugin_sql/)
- [@tauri-apps/plugin-sql on npm](https://www.npmjs.com/package/@tauri-apps/plugin-sql)
- [Official Store JavaScript reference](https://v2.tauri.app/reference/javascript/store/)

The official source confirms that relative SQLite URLs are resolved below the
Tauri AppConfig directory. It also confirms that registered migrations run on
the first `Database.load()` for that URL and that migrations execute in a
transaction.

## 4. Dependencies added

| Dependency | Type | Reason |
|---|---|---|
| `@tauri-apps/plugin-sql` 2.5.0 | npm runtime | Official WebView binding used only by the SQLite infrastructure adapter |
| `tauri-plugin-sql` 2.5.0, feature `sqlite` | Rust direct runtime crate | Official Tauri plugin, SQLite driver, connection lifecycle, and migrations |

No ORM, third-party SQLite wrapper, state library, router, filesystem plugin,
dialog plugin, or testing framework was added. MySQL and PostgreSQL features
are not enabled on the direct Rust dependency.

## 5. Database location

The connection URL is `sqlite:jardindigital.db`. For a relative SQLite URL,
the official plugin resolves the file below Tauri's OS-appropriate AppConfig
directory for `com.jardindigital.desktop`. It is not stored beside the
executable, in the repository, in Documents, or in a user-visible Vault.

## 6. Initial migration

Migration version `1`, description `create_nodes_table`, is registered in
Rust with the plugin's migration mechanism. It creates only:

```sql
CREATE TABLE IF NOT EXISTS nodes (
  id TEXT PRIMARY KEY NOT NULL,
  title TEXT NOT NULL,
  content TEXT NOT NULL,
  CHECK (length(trim(title)) > 0 OR length(trim(content)) > 0)
);
```

The ID is generated by JardinDigital, never by SQLite. No timestamps, status,
soft delete, version, metadata, JSON, tags, resource fields, canvas fields, or
AI fields are present. `Database.load()` applies the registered migration
automatically when the adapter first opens the database.

## 7. Vertical-slice architecture

```text
React validation UI
  -> Node application functions
  -> NodePersistence port
  -> SQLite Node adapter
  -> official Tauri SQL binding/plugin
  -> jardindigital.db in AppConfig
```

- `src/domain/node.ts` owns Node identity and content invariants.
- `src/application/nodePersistence.ts` defines the two-operation port, three
  small application functions, and explicit persistence error categories.
- `src/infrastructure/sqliteNodePersistence.ts` owns the connection URL, all
  SQL, parameter binding, row validation, and Domain rehydration.
- `src/main.tsx` is the composition root and injects the adapter into the UI.
- `src/App.tsx` is a temporary validation surface and contains no SQL or
  database binding import.

No generic repository, factory, manager, command bus, query bus, CQRS layer,
DI container, ORM, or empty symmetry directory was introduced.

## 8. Node rehydration

`createNode` remains the path for new Nodes and generates a Web Crypto UUID.
`rehydrateNode` is a separate Node-specific path that accepts the stored ID,
validates that it is an application UUID, normalizes title and content, rejects
both when empty or whitespace-only, and returns the stored ID unchanged. It
never calls `randomUUID`.

`editNode` preserves the existing ID and applies the same content normalization
and invariant without misusing the rehydration path for a user edit.

IDs regenerated while loading: **no**.

## 9. Minimum persistence contract

`NodePersistence` contains only:

- `save(node)`: inserts a new Node or updates the row with the same ID.
- `load(id)`: returns the rehydrated Node or `null` when no row exists.

There is no delete, list, search, pagination, or contract for another entity.

## 10. SQLite infrastructure

The adapter uses a lazily opened, reused `Database` connection. `save` uses a
parameterized SQLite upsert (`INSERT ... ON CONFLICT(id) DO UPDATE`) and writes
only `id`, `title`, and `content`. `load` selects those three columns with a
bound ID, verifies their runtime types, and calls `rehydrateNode`.

Plugin failures become `NodePersistenceError`. A row with unexpected types,
an invalid ID, or invalid Node content becomes `InvalidPersistedNodeError`.
Rows are never silently repaired and substitute IDs are never generated.

## 11. Application flow

- `createPersistedNode` creates a valid Domain Node and saves it.
- `loadPersistedNode` loads by stable ID and preserves the not-found `null`.
- `persistNodeEdit` produces a valid edit with the same ID and saves it.

These are functions rather than use-case base classes or a framework.

## 12. Temporary UI

The screen is explicitly titled **Persistence Vertical Slice**. It provides
only title/content fields, create-and-persist, load-by-ID, persist-edit,
reload-current, the current ID, and a status message. It distinguishes not
found, persistence failure, invalid persisted data, and Domain validation
failure. It is not the JardinDigital Home, Canvas, Library, or Capture UI.

## 13. Tauri permissions

| Capability/permission | Need |
|---|---|
| `core:default` | Existing base Tauri window behavior |
| `sql:default` | Official default SQL set: load, select, and close |
| `sql:allow-execute` | Parameterized insert/update upsert |

The plugin exposes permissions at command granularity, not per SQL statement.
For that reason the source boundary is important: components do not import the
binding and every statement lives in the one infrastructure adapter. No
filesystem, shell, HTTP, dialog, or other capability was added.

Arbitrary SQL in React components: **no**. Arbitrary filesystem access in the
UI: **no**.

## 14. Tests and verification levels

### Unit tests

The Domain suite contains 32 passing tests. Eight rehydration cases prove exact
ID preservation, title normalization, content normalization, each allowed
single-empty field, rejection of two empty/whitespace-only fields, rejection of
an invalid stored identity, and absence of UUID generation. The edit test
proves identity preservation.

### Automated integration test

None was added. The official plugin requires a Tauri runtime boundary, and a
mocked JavaScript database would not prove SQLite integration. No testing
framework was added merely to simulate it.

### Manual Tauri test

The real Windows Tauri/WebView2 application exercised the plugin, migration,
SQLite file, close/reopen boundary, upsert, select, and rehydration.

## 15. Manual restart result

Observed and confirmed on 2026-09-29:

- A Node was created and persisted, and its application-generated ID was
  recorded outside the repository for the duration of the test.
- The first application process ended completely with exit code 0.
- After reopening, loading by the recorded ID recovered the original title and
  content and preserved exactly the same ID.
- An edited title and content were persisted and recovered by a subsequent
  reload, again with the same ID.
- Everything worked correctly; no unexpected behavior was reported.
- The temporary ID and user-entered test content are intentionally not retained
  in the repository.

## 16. Limitations and deferred decisions

This slice persists only Node. It has no automated native integration harness,
backup/restore, import/export, search, or production UI. The SQL plugin's
capability model is command-granular; a future need for a cryptographically
narrower WebView/native boundary may justify dedicated Rust commands, but this
slice does not add that second abstraction preemptively.

Still deferred: Edge, Canvas, Placement, and Resource persistence;
Node/Resource relationships; filesystem resources; Managed/Linked Resource
operations and relink; previews and cache; backup and restore; Vault;
import/export; search/FTS; timestamps; soft delete; sync/cloud; AI and
embeddings; the production Canvas; and undo/redo.
